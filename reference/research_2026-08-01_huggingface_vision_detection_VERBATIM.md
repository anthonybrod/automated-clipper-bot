### Summary — what's genuinely worth considering vs. skip

**Face detection/tracking (category 1): MediaPipe BlazeFace remains correct, confirmed harder this round.** Three separate HF listings (`qualcomm/MediaPipe-Face-Detection`, `qualcomm/Lightweight-Face-Detection`, `STMicroelectronics/face_detect_front`) are either the *same* BlazeFace model repackaged or heavier alternatives with no speed advantage. The one plausible upgrade, `AdamCodd/YOLOv11n-face-detection` (Apache 2.0, real WIDERFACE-validated accuracy, 43 likes), trades away the exact property you selected BlazeFace for — it's meaningfully heavier per-frame than a 135K-parameter detector. No genuine lightweight alternative beats MediaPipe here. Recommendation: keep BlazeFace; don't switch.

**Emotion/expression recognition (category 2): real upgrade candidates exist.** `dima806/facial_emotions_image_detection` (Apache 2.0, 54K downloads/mo, 126 likes, claimed 91% accuracy) is a legitimately strong, actively-used, free, local ViT emotion classifier — a credible step up from `fer`. `py-feat/resmasknet` (MIT, part of an actively maintained 30-model toolkit updated this June) is the more "toolkit-equivalent" swap for `fer`/MTCNN specifically. Avoid `py-feat/face_multitask_v2` — non-commercial license and unnecessary Face-Mesh-grade weight for a task that only needs 7-way emotion classification. Recommendation: prototype `dima806`'s model as a frame-level emotion signal; keep it as an *additional* free signal, not a face-detector replacement.

**Game/scene detection (category 3): no free lunch found, and that's the honest finding.** No general pretrained "identify the game" model exists on HF worth adopting — only single-game classifiers (FC24) and one non-HF academic result (74.5% accuracy). This validates rather than replaces the existing `bendawg2010/Auto-clipper` per-game YOLOv8 pattern: you'd need one fine-tuned model per target game, same as that project already does for Arc Raiders. For "what game is being played" specifically, Twitch's own stream-category API metadata is free, exact, and already available — a vision model would be solving an already-solved problem worse.

**HF Spaces for reframing/highlights (category 4): thin pickings, one outright red herring.** `dvpearl/REFRAME` is *not* a video tool at all — confirmed by reading its actual README, it's an LLM feedback-tone-rewriter with zero connection to video reframing despite the name. `xcrop/long-video-to-shorts` and `frendyrachman/mlbb-ai-auto-clipper` are real, running Spaces in the right problem space, but both have essentially undocumented internals (metadata-only READMEs) and low-to-zero engagement (11 and 0 likes) — not verifiable reference implementations, just leads that would require reading their `app.py` source directly before trusting anything technical about them. `mostlycached/smart-cropper` is currently broken. None of these are worth integrating; none contradict or improve on the already-verified `openshorts`-sourced SmoothedCameraman/SpeakerTracker approach.

**Face Mesh vs. Face Detection explicitness, as requested**: every model checked in category 1 that outputs facial *landmarks* does so as a lightweight 6-point or similar sparse addition to a detection-grade model, not a heavy mesh — except `py-feat/face_multitask_v2`, which does output a full 478-point mesh (matching MediaPipe Face Mesh's point count) as one of seven simultaneous outputs. That model is correctly excluded on both license and weight grounds, and its inclusion here is a useful confirmation that a full mesh is overkill for this pipeline's actual need (bounding box + basic tracking, not landmark-level geometry).
